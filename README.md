Briefly summarize the requirements and goals of the app you developed. What user needs was this app designed to address?
I built a warehouse inventory app to replace paper counts and spreadsheets for tracking stock. The app needed secure account creation and login, an inventory grid, and fast ways to add items, remove them, and adjust quantities. It also needed to alert users via SMS when an item runs out. The goal was a simple tool that lets workers update counts quickly and find out about empty stock without checking every item.

What screens and features were necessary to support user needs and produce a user-centered UI for the app? How did your UI designs keep users in mind? Why were your designs successful?
The app ended up having three screens: login, sign-up, and the inventory grid. Login is the first screen, with a Sign Up link at the bottom, and sign-up returns to login when it finishes. I kept users in mind by placing the controls where they’re used. Each row has minus and plus buttons beside its quantity, plus an overflow menu for Edit and Delete, so a count change takes one tap. Delete asks for confirmation, so a stray tap can’t remove an item. The password fields hide their text with a show/hide toggle, and a bell icon with a badge shows how many items are out of stock. Each screen shows only the essential actions and shares the same colors, spacing, and button styles. The design worked because a first-time user can log in, add an item, and change its count without instructions.

How did you approach the process of coding your app? What techniques or strategies did you use? How could those techniques or strategies be applied in the future?
I built the app in layers. The XML layouts and styles came first, then a Room database with entities and DAOs for users and inventory, then the Activities that connect the screens to the data. Reusable helpers keep each class focused: a PasswordUtil class handles hashing, and a RecyclerView adapter communicates with MainActivity through a listener interface. I ran database work on a background executor and updated the UI on the main thread, which keeps the app responsive. I also built features one at a time and checked each before moving on. These habits apply to any future project: separate data, logic, and display; keep security code in one place; and add features incrementally so problems are easy to trace.

How did you test to ensure your code was functional? Why is this process important, and what did it reveal?
I tested by running the app on an Android emulator and working through each feature manually. That included creating an account, rejecting a duplicate username, logging in with correct and incorrect passwords, adding, editing, and deleting items, and driving a quantity to zero to trigger the badge and SMS alert. I also tested denying the SMS permission and turning alerts off, to confirm the app keeps working without notifications. When something failed, Logcat’s stack traces pointed to the cause. Testing matters because many problems only appear at runtime, and a successful build doesn’t mean the app works.

Consider the full app design and development process from initial planning to finalization. Where did you have to innovate to overcome a challenge?
The biggest challenge was balancing a simple interface with all the actions an inventory app needs. My original plan put add/remove and increase/decrease in a side menu, but that meant extra taps for the most common task. I redesigned the grid so quantity controls sit on each row and the less common actions sit in an overflow menu. A second challenge was SMS, the permission has to be requested while the app runs, and a denial couldn't break the app. I solved it with a settings dialog where users switch alerts on or off and enter a phone number, and the app turns alerts off automatically if permission is denied.

In what specific component of your mobile app were you particularly successful in demonstrating your knowledge, skills, and experience?
I’m most proud of the account and data layer. The sign-up process validates input, checks for duplicate usernames, and stores salted PBKDF2 password hashes in the Room database instead of plain text. Login uses a single error message for both an unknown username and a wrong password, so it doesn’t reveal which usernames exist. Together with the Room DAOs and the threading, this shows I can apply database design, background processing, and basic security practices in one working feature.
